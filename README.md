# Telegram Auth Extractor

![CI](https://github.com/mkaascs/TelegramAuthExtractor/actions/workflows/ci.yaml/badge.svg)
![Go](https://img.shields.io/badge/Go-1.26+-00ADD8?logo=go)

Микросервис, который извлекает данные авторизации Telegram — `auth_key`, `dc_id`, `user_id` — из клиента Telegram, запущенного внутри виртуального Android. Сервис управляет устройством через ADB + uiautomator: логинится, забирает файл сессии с устройства, достаёт из него permanent-ключи авторизации и проверяет их, переавторизуясь по MTProto.

Это то, что под капотом делает любой userbot-фреймворк или платформа управления аккаунтами: вход в настоящий мобильный клиент и извлечение полученных учётных данных, чтобы переиспользовать их программно — без устройства, из чистого Go.

## Запуск

### Требования

- Docker + Docker Compose
- (для локального запуска) Go 1.26+, [Task](https://taskfile.dev) и AVD в Android Studio (образ **без** Google Play — чтобы работал `adb root`)
- (для redroid) **Linux-хост с модулями ядра `binder` / `ashmem`** — redroid запускает Android на ядре хоста и не работает на стоковом Docker Desktop для macOS / Windows

### Переменные окружения

| Переменная | Описание | Обязательна |
|----------------------|------------------------------------------------------|-------------|
| `CONFIG_PATH` | Путь к YAML-конфигу | Да |
| `TELEGRAM_API_ID` | API id Telegram (с my.telegram.org) | Да |
| `TELEGRAM_API_HASH` | API hash Telegram | Да |
| `TELEGRAM_AUTH_KEY` | Извлечённый ключ для теста переавторизации (base64) | Нет |

Передаются через файл `.env` (подхватывается автоматически) или напрямую через окружение. Для Docker используется `config/redroid.yaml` (его `adb.serial` указывает на сервис `redroid`), для локального запуска — `config/local.yaml` (`emulator-5554`).

### Запуск через Docker

```bash
cp .env.example .env          # заполнить TELEGRAM_API_ID / TELEGRAM_API_HASH
docker-compose up --build
```

Поднимает redroid и сервис; сервис подключается к устройству по ADB, при необходимости ставит Telegram и отдаёт API на `localhost:8080`.

> И gotd-клиент, и клиент Telegram в Android должны достучаться до серверов Telegram. В сетях с ограничениями запускайте хост под системным (full-tunnel) VPN, чтобы трафик контейнеров тоже шёл через туннель.

### Локальный запуск

```bash
adb devices                   # убедиться, что эмулятор подключён
task run                      # запустить сервис (слушает :8080)
```

Другие полезные таски: `task test` / `task test:cover` (покрытие), `task lint`, `task generate:api` (перегенерировать REST-слой), `task test:reauth` (интеграционный тест переавторизации).

### Пример конфига (`config/local.yaml`)

```yaml
env: "local" # local, dev, prod
http_server:
  port: 8080
  write_timeout: 5s
  read_timeout: 10s
worker:
  code_wait: 3m
  cleanup_timeout: 30s
  queue_size: 50
adb:
  wait_timeout: 30s
  phone_check_timeout: 1m
  wait_interval: 0.8s
  package: "org.telegram.messenger.web"
  apk_url: "https://telegram.org/dl/android/apk"
  binary: "adb"              # или абсолютный путь, если adb не в PATH
  serial: "emulator-5554"
  needs_connect: false       # true для redroid (TCP)
```

## Возможности

- **Полная автоматизация логина** — сервис запускает Telegram, вводит номер телефона и код подтверждения через ADB, определяя экраны и закрывая первичные попапы через uiautomator (без слепых координат)
- **Ручной ввод кода** — код подтверждения передаётся через API и вводится в поле на экране; неверный код не фатален, а повторяется (`code_attempts` отслеживается и ограничен лимитом)
- **Извлечение сессии** — `tgnet.dat` читается прямо из приватного хранилища приложения с root-доступом
- **Независимый от версии парсинг** — permanent-ключи находятся по криптографическому инварианту, а не по фиксированным offset'ам, поэтому парсер переживает смену формата клиента с нулём ложных срабатываний
- **Определение домашнего DC** — извлечённые ключи параллельно пробуются против датацентров Telegram; тот, что авторизуется, даёт домашний `dc_id` и `user_id` аккаунта
- **Асинхронный пайплайн** — создание задачи возвращается сразу; фоновый worker ведёт её через жизненный цикл, клиент опрашивает статус
- **Идемпотентное создание задач** — повторный запрос по номеру с активной задачей возвращает существующую, а не создаёт дубликат
- **Сброс устройства** — после извлечения устройство возвращается в чистое состояние (`pm clear`), готовое к следующему номеру
- **Авто-провижининг** — если Telegram не установлен на устройстве, сервис скачивает и ставит APK при старте, с ретраями на нестабильной сети
- **OpenAPI-контракт** — REST-слой генерируется из spec-first OpenAPI 3 определения (`oapi-codegen`)
- **Graceful shutdown** — корректная остановка worker'а и HTTP-сервера по `SIGINT` / `SIGTERM`

## Архитектура

Чистая слоёная архитектура с зависимостями, направленными внутрь, связанными через интерфейсы:

- **`delivery`** — HTTP-хендлеры (chi) поверх сгенерированного OpenAPI-сервера, DTO-мапперы и middleware валидации запросов. Доменные ошибки маппятся в HTTP-коды; внутренние пути вызовов не утекают клиенту.
- **`services`** — бизнес-логика. `sessions.Service` — синхронный фасад, который дёргает REST-слой (создать задачу, прочитать статус, отправить код); `workers.Worker` — асинхронный исполнитель, ведущий жизненный цикл извлечения. Оба используют одно хранилище сессий.
- **`infra`** — адаптеры за интерфейсами, которые объявляют сервисы: `device` (ADB + uiautomator), `tgnet` (парсер ключей), `telegram` (verifier на gotd) и `storage` (in-memory репозиторий, заменяемый на реальную БД).
- **`domain`** — сущности, статусы жизненного цикла и ошибки, без фреймворочного кода.

Один worker владеет виртуальным устройством, поэтому одновременно выполняется одна задача; остальные ждут в буферизированном канале. Интерфейсы объявлены там, где потребляются, поэтому замена эмулятора на redroid — это изменение конфига, а не кода.

## API

Все маршруты смонтированы под `/api/v1`. REST-слой генерируется из [`api/openapi/v1/openapi.yaml`](api/openapi/v1/openapi.yaml) — `task generate:api` перегенерирует код сервера в `gen/rest/v1/`. Открой спеку в [Swagger Editor](https://editor.swagger.io), чтобы просмотреть интерактивно.

### Sessions

| Метод | Путь | Описание |
|----------|-------------------------------|-------------------------------------------------------|
| `POST` | `/api/v1/sessions` | Создать задачу извлечения (`202` создана / `200` идемпотентно) |
| `GET` | `/api/v1/sessions/{id}` | Статус задачи, включая `code_attempts` |
| `POST` | `/api/v1/sessions/{id}/code` | Отправить код подтверждения |
| `GET` | `/api/v1/sessions/{id}/result`| Извлечённые `dc_id` / `auth_key` / `user_id` (`409` пока не done) |
| `DELETE` | `/api/v1/sessions/{id}` | Отменить задачу и очистить устройство |

### Полный цикл

```bash
# 1. создать задачу
curl -s -X POST localhost:8080/api/v1/sessions \
  -H 'Content-Type: application/json' -d '{"phone":"+79991234567"}'

# 2. опрашивать, пока статус не станет "waiting_for_code"
curl -s localhost:8080/api/v1/sessions/<id>

# 3. отправить полученный код
curl -s -X POST localhost:8080/api/v1/sessions/<id>/code \
  -H 'Content-Type: application/json' -d '{"code":"12345"}'

# 4. когда статус "done" — забрать результат
curl -s localhost:8080/api/v1/sessions/<id>/result
```

## Пайплайн извлечения

Создание задачи ставит её в очередь фонового worker'а, который ведёт её через фиксированный жизненный цикл: `pending → logging_in → waiting_for_code → entering_code → extracting → cleanup → done` (неверный код возвращает в `waiting_for_code`; любая ошибка переводит в `failed`).

1. **Логин** — Telegram запускается, номер вводится через ADB. Переходы между экранами определяются опросом дерева UI (uiautomator), известные первичные попапы закрываются по мере появления.
2. **Код** — задача блокируется до прихода кода через `POST /code`, затем вводит его в поле на экране. Неверный код определяется и повторяется до лимита; отсутствие кода отваливается по таймауту.
3. **Извлечение** — как только достигнут список чатов, `tgnet.dat` читается с устройства и парсится во все permanent-ключи, которые в нём есть.
4. **Проверка** — ключи-кандидаты параллельно пробуются против датацентров Telegram; первый, что авторизуется (`users.getUsers(InputUserSelf)`), даёт домашний `dc_id` и `user_id`.
5. **Очистка** — устройство сбрасывается через `pm clear` независимо от исхода, чтобы следующая задача стартовала с чистого состояния.

## Извлечение ключей (криптографический якорь)

`tgnet.dat` хранит для каждого датацентра 256-байтный permanent `auth_key`, за которым идёт его 8-байтный `auth_key_id`, где `auth_key_id = SHA1(auth_key)[12:20]` (младшие 64 бита SHA1 ключа).

Парсер сканирует файл и считает 256-байтный блок ключом **тогда и только тогда**, когда следующие 8 байт равны `SHA1(block)[12:20]` — пересчитывая идентификатор из ключа и сверяя с тем, что хранится в файле. Вероятность случайного совпадения — 1/2⁶⁴, поэтому ложных срабатываний фактически нет, а метод опирается только на эту криптографическую связь, а не на раскладку полей файла — что делает его устойчивым к смене версии клиента Telegram. Домашний датацентр определяется затем эмпирически verifier'ом, а не читается из файла.

## Тест переавторизации

Отдельный тест доказывает, что извлечённые данные реально рабочие: берёт настоящий `auth_key` и переавторизует аккаунт по MTProto через [gotd](https://github.com/gotd/td), замыкая цикл от извлечения до переиспользования.

Так как тест ходит на живые серверы Telegram, он закрыт build-тегом `integration` и пропускается, если учётные данные не переданы — поэтому обычный `task test` и CI в сеть не ходят. Передайте извлечённый ключ (base64, прямо из `GET /sessions/{id}/result`) и свои API-данные в `.env`:

```dotenv
TELEGRAM_AUTH_KEY=<base64 auth_key>
TELEGRAM_API_ID=12345678
TELEGRAM_API_HASH=api_hash
```

```bash
task test:reauth
```

Тест загружает ключ в gotd-сессию, подключается и вызывает `users.getUsers(InputUserSelf)`; возвращённый `user_id` подтверждает, что извлечённые данные авторизуют аккаунт.

## Безопасность

- Извлечение нацелено на аккаунт, который ты авторизуешь сам — код подтверждения вводится вручную, поэтому сервис не действует от имени аккаунта, к которому нет доступа
- `auth_key` и `api_hash` — секреты и никогда не пишутся в логи (на уровне debug может появиться только нечувствительный `auth_key_id`)
- Ответы с ошибками санитизируются — клиент получает доменное сообщение, внутренние пути вызовов остаются только в логах
- Учётные данные (API id / hash) передаются через окружение, никогда не коммитятся в конфиг
- `.env`, `tgnet.dat`, файлы извлечённых ключей и APK Telegram — в `.gitignore`
